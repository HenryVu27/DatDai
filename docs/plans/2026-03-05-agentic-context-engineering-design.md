# Agentic Context Engineering Redesign

Date: 2026-03-05

## Problem

The current pipeline forces full RAG retrieval on every message, produces garbage on follow-up questions due to broken context management, and wastes compute on greetings/simple follow-ups. No intelligence decides whether retrieval is needed.

## Solution: Orchestrator-First Architecture

Replace the sequential RAG pipeline with a two-stage agentic flow: an orchestrator LLM decides what tools to call, then a generator LLM produces the answer.

## Model Configuration

| Role | Model | Purpose |
|------|-------|---------|
| Orchestrator | gemini-3-flash-preview | Tool-use decisions, every turn |
| Generator (complex) | gemini-3.1-pro-preview | Nuanced legal answers |
| Generator (simple) | gemini-3-flash-preview | Straightforward answers |
| Utility | gemini-3.1-flash-lite-preview | Query rewrite fallback |
| Embedding | gemini-embedding-001 | Unchanged |
| Fallbacks | gemini-2.5-pro, 2.5-flash, 2.5-flash-lite | If preview models are down |

## Pipeline Flow

```
User message
    |
    v
[1. Assemble context] -- load summary, trim history, build prompt
    |
    v
[2. Orchestrator call] -- Flash 3, returns structured JSON
    |
    +--> direct_response set? --> return immediately
    |
    +--> actions empty? --> skip to generator (no RAG context)
    |
    +--> actions present:
         |
         [3. Execute tools in parallel]
         |   - search_legal_docs -> hybrid search + rerank
         |   - lookup_amendment -> amendment_index + metadata fetch
         |   - lookup_specific_dieu -> metadata fetch + full dieu expand
         |
         [4. Merge & deduplicate chunks]
         |
         v
[5. Generator call] -- Pro 3.1 or Flash 3 based on complexity
    |
    v
[6. Citation check] -- verify against retrieved chunks
    |
    v
[7. Save to DB] -- message + sources + summary_update if present
    |
    v
Response
```

## Orchestrator Design

Input: system prompt (XML-tagged) + conversation summary + last 6 turn-groups + current message.

Output (structured JSON):
```json
{
  "reasoning": "short chain-of-thought",
  "actions": [
    {"tool": "search_legal_docs", "query": "...", "filters": {"doc_ids": [...], "dieu": "..."}},
    {"tool": "lookup_amendment", "target_doc": "nd102", "dieu": "Dieu 15"},
    {"tool": "lookup_specific_dieu", "doc_id": "ldd2024", "dieu": "Dieu 79"}
  ],
  "complexity": "complex | simple",
  "summary_update": "rolling summary update or null",
  "direct_response": "direct answer or null"
}
```

Tools available to orchestrator:

- **search_legal_docs** -- hybrid search against Qdrant. Orchestrator crafts the query.
- **lookup_amendment** -- check amendment relationships between decrees (deterministic).
- **lookup_specific_dieu** -- fetch a specific Dieu from a specific document by metadata.

Orchestrator does NOT call tools when: greetings, answer already in conversation, needs to ask clarification.

## Context Assembly

System prompt uses XML-tagged sections, static prefix first for KV-cache:

```xml
<identity>...</identity>           (static)
<boundaries>...</boundaries>       (static)
<legal-hierarchy>...</legal-hierarchy>  (static)
<tools>...</tools>                 (orchestrator only, static)
--- volatile below ---
<conversation-summary>...</conversation-summary>
<recent-messages>...</recent-messages>
```

Trimming rules:
- Keep last 6 turn-groups (user+assistant as atomic pairs)
- Max 30K chars for conversation section
- Remove oldest complete turn-groups first
- Summary covers everything before retained window
- Chained summaries: new summary builds on previous summary

Summary is generated by the orchestrator as a byproduct (summary_update field), not as a separate LLM call.

## Key Design Principles (from henryvu.blog)

1. Pull-based retrieval -- model decides when to retrieve via tool calls
2. Tiered compression -- raw recent turns + chained summaries for older
3. Atomic turn-group trimming -- never orphan messages
4. XML-tagged system prompts -- structured, cache-friendly
5. Static prefix first -- volatile content last for KV-cache optimization
6. Removal over addition -- delete HyDE, decomposer, auto-cross-ref
7. Isolation -- separate orchestrator and generator concerns
